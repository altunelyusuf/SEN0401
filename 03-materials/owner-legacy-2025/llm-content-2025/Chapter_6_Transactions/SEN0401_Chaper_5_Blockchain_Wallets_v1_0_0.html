Module 1

Wallet Fundamentals

Understanding the true nature of cryptocurrency wallets - they contain keys, not coins.

Key Insight

"A common misconception about bitcoin is that bitcoin wallets contain bitcoin. In fact, the wallet contains only keys. The 'coins' are recorded on the blockchain. Users control the coins on the network by signing transactions with the keys in their wallets."

— Andreas M. Antonopoulos, Mastering Bitcoin (2017)
Beginner

What is a Wallet?

A blockchain wallet is a software application or hardware device that serves as the primary user interface to a blockchain network. It manages:

  • Private Keys - Secret numbers that authorize spending
  • Public Keys - Derived from private keys, used for verification
  • Addresses - Derived from public keys, shared with others to receive funds
  • Transaction Signing - Creating valid blockchain transactions
Analogy: A wallet is like a keychain - it holds the keys to your coins, not the coins themselves. The coins remain on the blockchain (like money in a bank vault), and your keys prove you own them.
Intermediate

Private Keys

A private key is a 256-bit random number that must be kept secret. It's the foundation of cryptocurrency ownership.

Example Private Key (Hex)

Size: 256 bits (32 bytes)
Range: 1 to n-1 (where n = secp256k1 order)
Possible Keys: ~2256 ≈ 1077
Critical: Anyone who obtains your private key can spend your funds. Never share it!

Public keys are derived from private keys using Elliptic Curve Cryptography (ECC) on the secp256k1 curve.

Nondeterministic (JBOK) Wallets

"Just a Bunch Of Keys" - Each private key is generated independently from a random number with no mathematical relationship between keys.

Problems
  • Must backup every key individually
  • Pool exhaustion requires fresh backups
  • Cumbersome for frequent address generation
  • High risk of lost funds due to backup failure
Historical Context
  • Used by original Bitcoin Core client
  • Pre-generated pools of ~100 keys
  • Required backup after pool exhaustion
  • Superseded by BIP-32 HD wallets
JBOK Key Generation (Pseudocode) 
// Each key is completely independent
function generateJBOKWallet(numKeys) {
    const wallet = { keys: [] };
    
    for (let i = 0; i < numKeys; i++) {
        // Generate random 256-bit number
        const privateKey = crypto.randomBytes(32);
        
        // Derive public key using secp256k1
        const publicKey = secp256k1.getPublicKey(privateKey);
        
        // Generate address
        const address = hash160(publicKey);
        
        wallet.keys.push({ privateKey, publicKey, address });
        // ⚠️ Each key must be backed up separately!
    }
    
    return wallet;
}
Type-2 • Recommended

Hierarchical Deterministic (HD) Wallets

HD wallets derive all keys from a single master seed using a tree structure. A single backup protects all current and future keys.

Advantages
  • Single seed backup for unlimited keys
  • Organized tree structure (accounts, chains)
  • Can share branch public keys safely
  • Standardized across wallets (BIP-32/44)
Key Features
  • Deterministic derivation path
  • Hardened vs. normal child keys
  • Extended public keys (xpub)
  • Industry standard since 2012

Hierarchical Deterministic Wallets

The foundational specification for deriving a tree of keys from a single seed. All modern wallets implement BIP-32.

Master Seed Generation

The master seed is generated from random entropy (128-256 bits). This seed is the single backup point for the entire wallet.

Master Key Derivation 
// BIP-32 Master Key Generation
function generateMasterKey(seed) {
    // HMAC-SHA512 with key "Bitcoin seed"
    const I = HMAC_SHA512("Bitcoin seed", seed);
    
    // Split 512-bit result
    const masterPrivateKey = I.slice(0, 32);  // Left 256 bits
    const masterChainCode = I.slice(32, 64);  // Right 256 bits
    
    return { masterPrivateKey, masterChainCode };
}

Child Key Derivation (CKD)

Children are derived using the parent key, chain code, and an index. Supports both normal and hardened derivation.

Normal Derivation (index < 2³¹)
  • Uses parent public key
  • Extended public key can derive child public keys
  • Useful for watch-only wallets
  • ⚠️ Vulnerable if child private key is leaked
Hardened Derivation (index ≥ 2³¹)
  • Uses parent private key
  • Notation: index' or indexH
  • More secure isolation between branches
  • Cannot derive from xpub alone

Extended Keys (xprv / xpub)

Extended keys combine a key with its chain code, allowing derivation of child keys.

From Mnemonic to Seed

The mnemonic is converted to a 512-bit seed using PBKDF2-HMAC-SHA512 with 2048 iterations.

Seed Derivation (PBKDF2) 
// BIP-39: Mnemonic to Seed
function mnemonicToSeed(mnemonic, passphrase = "") {
    // Normalize mnemonic (NFKD)
    const normalizedMnemonic = mnemonic.normalize("NFKD");
    
    // Salt = "mnemonic" + optional passphrase
    const salt = "mnemonic" + passphrase.normalize("NFKD");
    
    // PBKDF2 with 2048 iterations
    const seed = PBKDF2_HMAC_SHA512(
        normalizedMnemonic,  // Password
        salt,                // Salt
        2048,                // Iterations
        64                   // Output length (512 bits)
    );
    
    return seed;  // 512-bit seed for BIP-32
}
Passphrase Feature: The optional passphrase creates a completely different wallet from the same mnemonic. This enables "plausible deniability" - you can have a decoy wallet with the empty passphrase.

Multi-Party Computation

MPC Wallets: Distributed Key Management

MPC eliminates single points of failure by distributing key generation and signing across multiple parties, without ever reconstructing the full private key.

Transaction Signing
Party A Share 1
Party B Share 2
Party C Share 3

How MPC Works

  1. Distributed Key Generation (DKG): Multiple parties collaboratively generate key shares without any single party knowing the full key.
  2. Threshold Signing: A subset (e.g., 2-of-3) compute partial signatures that combine into a valid signature.
  3. No Key Reconstruction: The private key is never assembled - security is maintained throughout.

MPC Protocols

FROST 2020

Flexible Round-Optimized Schnorr Threshold

  • 2-round signing protocol
  • Schnorr signatures (Taproot compatible)
  • No trusted dealer required
  • Preprocessing for 1-round signing
Best for: Bitcoin Taproot
GG18/GG20 2018-2020

Gennaro-Goldfeder Protocol

  • Threshold ECDSA
  • Works with Ethereum
  • 9 communication rounds
  • Paillier encryption
Best for: Ethereum, pre-Taproot BTC
Lindell17 2017

Two-Party ECDSA

  • Only 2 rounds
  • Simple 2-of-2 setup
  • No threshold flexibility
  • ZK proofs + OT
Best for: Consumer wallets (ZenGo)

MPC vs. Traditional Multisig

MPC Wallets
  • Single standard signature on-chain
  • Constant transaction fees
  • Policy hidden from blockchain
  • Off-chain key resharing
  • Complex cryptography
  • Requires secure communication
VS
Multisig Wallets
  • Simple, well-understood
  • On-chain transparency
  • Native blockchain support
  • Higher fees (more data)
  • Policy visible on-chain
  • Inflexible key changes
MPC Threshold Signing (Conceptual) 
// Simplified MPC 2-of-3 Threshold Signing
class MPCWallet {
    constructor(threshold, totalParties) {
        this.t = threshold;  // 2
        this.n = totalParties;  // 3
        this.shares = [];  // Each party holds one share
    }
    
    // Distributed Key Generation - no single party knows full key
    async distributedKeyGen() {
        // Each party generates random polynomial of degree t-1
        // Shares are distributed via secure channels
        // Public key is computable without revealing private key
        return { publicKey: this.computePublicKey() };
    }
    
    // Threshold signing - only t parties needed
    async sign(message, participatingParties) {
        if (participatingParties.length < this.t) {
            throw new Error(`Need at least ${this.t} parties`);
        }
        
        // Each party computes partial signature
        const partialSigs = await Promise.all(
            participatingParties.map(party => 
                party.computePartialSignature(message)
            )
        );
        
        // Combine partial signatures (Lagrange interpolation)
        const fullSignature = this.combineSignatures(partialSigs);
        
        // Result is a standard signature - indistinguishable from single-key
        return fullSignature;
    }
}
Account Abstraction

ERC-4337: Programmable Wallets on Ethereum

Account Abstraction transforms wallets from simple key-holders into programmable smart contracts, enabling custom validation logic, gas sponsorship, and social recovery.

Traditional EOA

Legacy
  • Fixed ECDSA validation only
  • Must hold ETH for gas
  • No batching transactions
  • No recovery options
  • Single signature required
ERC-4337

Smart Contract Wallet

Modern
  • Custom validation logic
  • Gasless transactions (Paymasters)
  • Batch multiple operations
  • Social recovery / guardians
  • Multisig, MPC, passkeys

ERC-4337 Architecture

UserOperation

A data structure containing the user's intent: sender, calldata, gas limits, and signatures. Not a real transaction until bundled.

Bundler

Off-chain actors that collect UserOperations, validate them, and submit batches to the EntryPoint as regular transactions.

EntryPoint

A singleton smart contract that validates and executes UserOperations. The trusted coordinator for all ERC-4337 accounts.

Paymaster

Optional contracts that sponsor gas fees, enabling gasless UX. Can accept ERC-20 tokens or implement subscription models.

EIP-7702 • Pectra Upgrade (May 2025)

Native EOA Delegation

EIP-7702 allows EOAs to temporarily delegate to smart contract code, bringing account abstraction benefits to existing accounts without migration.

Social Recovery

Guardian-Based Wallet Recovery

Social recovery replaces seed phrase backup with trusted guardians who can help restore access without ever controlling your funds.

1
Setup Guardians

Designate 3-5 trusted parties (friends, family, hardware wallets, institutions)

2
Loss Event

Device lost, key compromised, or access needed

3
Guardian Approval

M-of-N guardians approve new signing key (e.g., 2-of-3)

4
Time Delay

24-48 hour security delay to detect malicious recovery

Access Restored

New key controls wallet; old key revoked

Guardian Types

Friends & Family

Trusted individuals who verify your identity

Hardware Wallet

Your own cold storage as backup guardian

Institutional

Wallet provider or custodian service

ZK-Email

Prove email ownership via DKIM + ZK proofs

Vitalik's 2024 Recommendation: Start with 2-of-3 guardians (zk-email + local device + provider backup) for new users. Expand guardian set as assets grow.

Security Best Practices

Never Reuse Addresses

Generate fresh addresses for each transaction to enhance privacy and prepare for quantum threats.

Metal Seed Backup

Store mnemonic on steel/titanium plates. Paper degrades; metal survives fire and water.

Verify on Device

Always confirm addresses and amounts on hardware wallet screen, never trust computer display alone.

Use Time Delays

Enable withdrawal delays on smart wallets to detect and cancel malicious transactions.

Air-Gap When Possible

Use QR codes or SD cards instead of USB for signing, eliminating network-based attacks.

Test Recovery

Periodically verify your seed backup works by testing on a separate device with small amounts.
