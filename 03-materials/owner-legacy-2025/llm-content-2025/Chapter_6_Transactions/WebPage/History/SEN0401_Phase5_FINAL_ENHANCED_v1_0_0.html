📋 Module 1: Transaction Fundamentals

Understanding the core structure and mechanics of blockchain transactions.

1.1 What is a Bitcoin Transaction?

Transactions are the most important part of the bitcoin system. Everything in Bitcoin is designed to ensure that transactions can be created, propagated on the network, validated, and finally added to the global ledger of transactions (the blockchain).

💡 Key Insight: Transactions are data structures that encode the transfer of value between participants in the Bitcoin system. Each transaction is a public entry in Bitcoin's blockchain, the global double-entry bookkeeping ledger.

A Bitcoin transaction is fundamentally different from traditional payment systems. Rather than moving funds from one account to another, Bitcoin transactions consume previously created outputs and create new outputs that can be consumed in future transactions. This creates an unbroken chain of value transfer from the creation of bitcoin through mining to the present day.

1.2 Transaction Structure: Behind the Scenes

What you see in a blockchain explorer is very different from what a transaction actually contains. Most high-level constructs like "addresses" and "balances" don't actually exist in the transaction data—they're abstractions created for user convenience.

Example: Raw Transaction Structure

{
  "version": 1,
  "locktime": 0,
  "vin": [{
    "txid": "7957a35f...999f6f18",
    "vout": 0,
    "scriptSig": "3045022100...[signature]...",
    "sequence": 4294967295
  }],
  "vout": [{
    "value": 0.01500000,
    "scriptPubKey": "OP_DUP OP_HASH160 ab68025... OP_EQUALVERIFY OP_CHECKSIG"

    "scriptPubKey": "OP_DUP OP_HASH160 7f9b1a7... OP_EQUALVERIFY OP_CHECKSIG"
  }]
}
⚠️ Important: In Bitcoin, there are no coins, no senders, no recipients, no balances, no accounts, and no addresses at the protocol level. All of these concepts are constructed at a higher level for user convenience.

1.3 The UTXO Model: Understanding Bitcoin's Accounting System

The fundamental building block of a Bitcoin transaction is a transaction output. Transaction outputs are indivisible chunks of bitcoin currency, recorded on the blockchain and recognized as valid by the entire network.

🔑 Key Concept: UTXO (Unspent Transaction Output)

UTXO stands for Unspent Transaction Output. Bitcoin full nodes track all available and spendable outputs in what's called the UTXO set. The UTXO set currently numbers in the millions of individual outputs.

Every transaction represents a state transition in the UTXO set: consuming (spending) existing UTXOs and creating new ones.

💰 Understanding "Balance" in Bitcoin

When we say a user's wallet has "received" bitcoin, what we really mean is that the wallet has detected a UTXO that can be spent with one of the keys controlled by that wallet.

A user's bitcoin "balance" is the sum of all UTXO that the user's wallet can spend, which may be scattered among hundreds of transactions and hundreds of blocks. The concept of balance is created by the wallet application, not by the Bitcoin protocol.

📊 UTXO Set Dynamics

✅ Wallet UTXO Set
UTXO #1: 0.5 BTC
UTXO #2: 0.3 BTC
UTXO #3: 0.2 BTC
Total: 1.0 BTC
🔄 After Transaction
UTXO #1: 0.5 BTC (spent)
UTXO #2: 0.3 BTC
UTXO #3: 0.2 BTC
UTXO #4: 0.3 BTC (change)
Total: 0.8 BTC
(0.2 BTC sent + 0.001 BTC fee)

Critical UTXO Properties

🔒 Indivisible

UTXOs cannot be divided. If a UTXO is larger than the desired payment amount, it must be consumed in its entirety and change must be generated.

Example: To pay 1 BTC from a 20 BTC UTXO, you must consume all 20 BTC and create two outputs: 1 BTC to recipient, 19 BTC back as change.
📏 Discrete Units

Outputs are discrete units of value denominated in integer satoshis. One bitcoin can be divided down to eight decimal places (100,000,000 satoshis = 1 BTC).

Satoshi: The smallest unit in Bitcoin, named after its creator. 1 satoshi = 0.00000001 BTC

🔐 Module 2: Transaction Inputs and Outputs Deep Dive

Understanding how transactions consume and create value through inputs and outputs.

2.1 Transaction Outputs: Creating Spendable Value

Every Bitcoin transaction creates outputs, which are recorded on the blockchain ledger. Almost all of these outputs create spendable chunks of bitcoin called UTXO, which are recognized by the whole network and available for the owner to spend in a future transaction.

📦 Transaction Output Components

Transaction outputs consist of two critical parts:

  1. An amount of bitcoin, denominated in satoshis (the smallest bitcoin unit)
  2. A cryptographic puzzle (locking script) that determines the conditions required to spend the output

Output Structure in JSON

"vout": [
  {
    "value": 0.01500000,
    "scriptPubKey": "OP_DUP OP_HASH160 ab68025513c3dbd2f7b92a94e0581f5d50f654e7 
                     OP_EQUALVERIFY OP_CHECKSIG"
  },
  {
    "value": 0.08450000,
    "scriptPubKey": "OP_DUP OP_HASH160 7f9b1a7fb68d60c536c2fd8aeaa53a8f3cc025a8 
                     OP_EQUALVERIFY OP_CHECKSIG"
  }
]
💡 Key Insight: The scriptPubKey (locking script) is also known as a:
  • Locking script (what we call it in this course)
  • Witness script (in SegWit context)
  • Cryptographic puzzle (conceptual term)

Output Serialization Format

Size Field Description

2.2 Transaction Inputs: Consuming Previous Outputs

Transaction inputs identify which UTXO will be consumed and provide proof of ownership through an unlocking script. To build a transaction, a wallet selects from the UTXO it controls—choosing UTXO with enough value to make the requested payment.

🔑 Transaction Input Components

Each input contains four essential elements:

  1. Transaction ID (txid): References the transaction containing the UTXO being spent
  2. Output Index (vout): Identifies which specific output from that transaction (zero-indexed)
  3. Unlocking Script (scriptSig): Satisfies the conditions placed on the UTXO, unlocking it for spending
  4. Sequence Number: Used for transaction replacement and timelocks

Input Structure in JSON

"vin": [{
  "txid": "7957a35fe64f80d234d76d83a2a8f1a0d8149a41d81de548f0a65a8a999f6f18",
  "vout": 0,
  "scriptSig": "3045022100884d142d....[signature]....
                0484ecc0d46f1918b309....[public key]....",
  "sequence": 4294967295
}]

⚠️ Critical Understanding: Transaction inputs do NOT explicitly state the value being spent! To know the input value, you must retrieve the referenced UTXO from the blockchain. This is why validators must look up previous transactions to verify the current one.

2.3 Transaction Fees: The Economic Incentive

Transaction fees are a crucial part of Bitcoin's economic model, providing incentives for miners to include transactions in blocks. Understanding how fees work is essential for creating valid transactions.

💰 Fee Calculation Formula

Fees = Sum(Inputs) − Sum(Outputs)

The fee is implicit—there's no fee field in the transaction structure. Any excess amount remaining after all outputs are deducted from all inputs becomes the miner's fee.

📊 Fee Calculation Example

Inputs
UTXO #1: 0.8 BTC
UTXO #2: 0.3 BTC
Total Inputs: 1.1 BTC
Outputs
Payment: 0.5 BTC
Change: 0.599 BTC
Total Outputs: 1.099 BTC
Fee: 0.001 BTC
🚨 Common Mistake: If you forget to create a change output, the entire "leftover" amount becomes the transaction fee! For example, consuming a 20 BTC UTXO to pay 1 BTC without creating a 19 BTC change output means you just paid a 19 BTC fee to the miner.

⚙️ Dynamic Fee Estimation

Modern Bitcoin wallets use dynamic fee estimation based on network congestion. Fees are typically measured in satoshis per byte (sat/byte or sat/vB for virtual bytes in SegWit).

🚀 High Priority

80+ sat/byte

Next block confirmation (0-1 blocks)

⏱️ Medium Priority

40-60 sat/byte

3-6 blocks (~30-60 minutes)

🐌 Low Priority

20-30 sat/byte

6+ blocks (1+ hours)

💡 Important: Static fees are no longer viable. Wallets that set static fees produce poor user experience as transactions may get "stuck" in the mempool, remaining unconfirmed for extended periods.

2.4 Change Outputs: Managing UTXO Indivisibility

Because UTXOs are indivisible, most Bitcoin transactions generate change. Understanding change outputs is crucial for both wallet developers and users who construct raw transactions.

🏪 Real-World Analogy

Imagine buying a $1.50 beverage. You reach into your wallet and find:

  • Exact change: $1 bill + 2 quarters = perfect!
  • Overpayment: $5 bill → receive $3.50 change
  • Multiple small bills: 6 quarters → exact amount

Bitcoin transactions work the same way. The wallet automatically selects UTXOs and creates change when necessary—users never see this complexity.

🔐 Module 3: Bitcoin Script Language and Validation

Understanding the programmable scripting system that secures Bitcoin transactions.

3.1 What is Bitcoin Script?

The Bitcoin transaction script language, called Script, is a Forth-like reverse-polish notation stack-based execution language. Both the locking script (placed on a UTXO) and the unlocking script (provided when spending) are written in this language.

🎯 Script Design Philosophy

Script is deliberately designed to be:

  • Simple: Limited scope, minimal processing requirements
  • Predictable: Deterministic execution, no randomness
  • Stateless: No state before or after execution
  • Turing Incomplete: No loops or complex flow control
  • Secure: Cannot create denial-of-service vulnerabilities
💡 Key Insight: Bitcoin transaction validation is not based on static patterns but achieved through execution of a scripting language. This allows for a nearly infinite variety of conditions to be expressed—the power of "programmable money."

⚙️ Turing Incompleteness: A Security Feature

Script contains many operators but deliberately lacks loops and complex flow control. This ensures the language is not Turing Complete, meaning scripts have limited complexity and predictable execution times.

✅ Benefits of Turing Incompleteness
  • Prevents infinite loops
  • Blocks "logic bombs"
  • Ensures predictable execution time
  • Protects against DoS attacks
  • Every transaction validated by every full node
❌ What Script Cannot Do
  • Create loops (for, while)
  • Maintain state between executions
  • Access external data
  • Perform arbitrary computations
  • Execute unpredictably

3.2 Stack-Based Language: Understanding the Stack

Script uses a data structure called a stack—a Last-In-First-Out (LIFO) queue. Think of it like a stack of cards where you can only add or remove from the top.

📚 Stack Operations

PUSH

Adds an item on top of the stack

Stack: [3, 2, 1]
↓ PUSH 4
Stack: [4, 3, 2, 1]
POP

Removes the top item from the stack

Stack: [4, 3, 2, 1]
↓ POP → 4
Stack: [3, 2, 1]

📊 Script Execution Example: 2 3 OP_ADD 5 OP_EQUAL

Step 1:
PUSH 2
Stack: [2]
Step 2:
PUSH 3
Stack: [3, 2]
Step 3:
OP_ADD
Pop 3, Pop 2
3 + 2 = 5
Stack: [5]
Step 4:
PUSH 5
Stack: [5, 5]
Step 5:
OP_EQUAL
Pop 5, Pop 5
5 == 5 → TRUE
Stack: [TRUE]
Result:
✅
Valid!
TRUE on stack
💡 Key Point: A script is valid if and only if the top item on the stack is TRUE (represented by the number 1 or any non-zero value) after execution. FALSE is represented by zero or an empty stack.

3.3 Locking and Unlocking Scripts

Bitcoin's validation engine uses two types of scripts that work together to validate transactions:

🔒 Locking Script (scriptPubKey)

A spending condition placed on an output. It specifies the conditions that must be met to spend the output in the future.

Also known as:

  • scriptPubKey (legacy name)
  • Witness script (SegWit context)
  • Cryptographic puzzle

🔓 Unlocking Script (scriptSig)

A script that "solves" or satisfies the conditions placed on an output by a locking script, allowing the output to be spent.

Also known as:

  • scriptSig (legacy name)
  • Witness (SegWit context)

⚙️ Script Validation Process

1️⃣ Copy Unlocking Script from Current Transaction Input
<Signature> <Public Key>
↓
2️⃣ Retrieve Locking Script from Referenced UTXO
OP_DUP OP_HASH160 <PubKeyHash> OP_EQUALVERIFY OP_CHECKSIG
↓
3️⃣ Concatenate and Execute Combined Script
<Signature> <Public Key> OP_DUP OP_HASH160 <PubKeyHash> OP_EQUALVERIFY OP_CHECKSIG
↓
4️⃣ Validation Result
✅

Input is valid if and only if execution results in TRUE on the stack

🔐 Security Note: The UTXO is permanently recorded in the blockchain and is unaffected by failed spending attempts. Only a valid transaction that correctly satisfies the conditions of the output results in the output being considered "spent" and removed from the UTXO set.

3.4 P2PKH: The Most Common Transaction Type

Pay-to-Public-Key-Hash (P2PKH) is the most common transaction script pattern, used in the majority of Bitcoin transactions. It's what people typically mean when they talk about "sending bitcoin to an address."

🔑 P2PKH Script Pattern

Locking Script (scriptPubKey):
OP_DUP OP_HASH160 <PubKeyHash> OP_EQUALVERIFY OP_CHECKSIG
Unlocking Script (scriptSig):
<Signature> <Public Key>

🔄 P2PKH Execution Step-by-Step

Combined Script:

<Sig> <PubKey> OP_DUP OP_HASH160 <PubKeyHash> OP_EQUALVERIFY OP_CHECKSIG
Step 1: PUSH <Sig>
[Sig]
Step 2: PUSH <PubKey>
[PubKey, Sig]
Step 3: OP_DUP
[PubKey, PubKey, Sig]
Step 4: OP_HASH160
[PubKeyHash', PubKey, Sig]
Step 5: PUSH <PubKeyHash>
[PubKeyHash, PubKeyHash', PubKey, Sig]
Step 6: OP_EQUALVERIFY
Verify hashes equal
[PubKey, Sig]
Step 7: OP_CHECKSIG
Verify signature
[TRUE]
✅ VALID
🔐 What P2PKH Proves:
  1. The public key hashes to the expected public key hash (proves address ownership)
  2. The signature is valid for this transaction and public key (proves private key ownership)

🔐 Module 4: Multisignature Transactions

Multisignature (multisig) transactions require multiple signatures to authorize spending, enabling shared control, corporate governance, and enhanced security.

4.1 Understanding M-of-N Multisignature Schemes

Multisignature scripts set a condition where N public keys are recorded in the script and at least M of those must provide signatures to unlock the funds. This is known as an M-of-N scheme, where N is the total number of keys and M is the threshold of signatures required for validation.

📐 M-of-N Scheme Parameters

  • N: Total number of public keys listed in the script (max 15 in standard transactions)
  • M: Minimum threshold of signatures required (M ≤ N)
  • Examples: 2-of-3 (2 signatures from 3 keys), 3-of-5 (3 from 5), 1-of-1, 15-of-15

General Multisignature Script Format

M <Public Key 1> <Public Key 2> ... <Public Key N> N CHECKMULTISIG

Example: 2-of-3 Multisig Locking Script

2 <Public Key A> <Public Key B> <Public Key C> 3 CHECKMULTISIG

⚠️ CHECKMULTISIG Bug: The Off-By-One Error

Critical Implementation Detail: Due to a bug in CHECKMULTISIG's original implementation, the opcode pops one extra value from the stack (M+1 instead of M). This bug became part of the consensus rules and must be replicated forever.

Workaround: Add a dummy 0 at the beginning of unlocking scripts: 

// Incorrect (won't work):
<Signature B> <Signature C>

// Correct (with dummy 0):
0 <Signature B> <Signature C>

💼 Corporate Accounts Receivable

Company uses 2-of-3 multisig (owner + partner OR owner + attorney) for customer payments, providing governance controls and protection against theft or embezzlement.

🏦 Escrow Services

2-of-3 scheme with buyer, seller, and arbitrator. Funds released when any two parties agree, enabling fair dispute resolution without single point of control.

🔐 Personal Security

2-of-3 with keys on laptop, phone, and hardware wallet. Protects against single device compromise while maintaining spending ability if one key is lost.

🏛️ DAO Governance

5-of-9 or higher thresholds for decentralized organizations, requiring majority consensus among board members for treasury movements.

4.2 Pay-to-Script-Hash (P2SH): Simplifying Complex Scripts

Pay-to-Script-Hash (P2SH) was introduced in 2012 (BIP16) as a powerful abstraction that greatly simplifies the use of complex transaction scripts. Instead of including the full script in the output, P2SH replaces it with a cryptographic hash, deferring script revelation until spending time.

💡 The P2SH Innovation

P2SH means: "Pay to a script matching this hash, a script that will be presented later when this output is spent."

This shifts complexity, data storage, and transaction fees from the sender (payment time) to the recipient (spending time), making complex scripts as easy to use as simple bitcoin addresses.

Comparison: Direct Multisig vs P2SH-Wrapped Multisig

Attribute Direct Multisig P2SH Multisig
Locking Script Full multisig script (~500 bytes) 20-byte hash only
Sender Burden Must obtain full script, pay large fee Just needs P2SH address (like regular address)
UTXO Set Size Large (full script in RAM) Small (only hash in RAM)
Blockchain Storage At payment time (output) At spending time (input)
Privacy Script details public immediately Script details revealed only when spent

P2SH Address Creation Process

// Step 1: Create redeem script (e.g., 2-of-3 multisig)
redeemScript = "2 <PubKey A> <PubKey B> <PubKey C> 3 CHECKMULTISIG"

// Step 2: Hash the redeem script
scriptHash = RIPEMD160(SHA256(redeemScript))

// Step 3: Create P2SH locking script
lockingScript = "OP_HASH160 <scriptHash> OP_EQUAL"

// Step 4: Encode as address (starts with '3' on mainnet)
p2shAddress = Base58Check(0x05 + scriptHash)
// Example: 3F6i6kwkevjR7AsAd4te2YB2zZyASEm1HM

🔍 P2SH Two-Stage Validation

  1. Stage 1: Check that the hash of the presented redeem script matches the hash in the locking script
  2. Stage 2: Execute the redeem script with the remaining stack data to verify spending conditions

This two-stage process allows any valid script to be wrapped in P2SH, enabling experimentation with novel transaction types while maintaining backward compatibility.

4.3 Timelocks: Adding the Time Dimension

Timelocks are restrictions on transactions or outputs that only allow spending after a point in time. They extend Bitcoin scripting into the time dimension, enabling complex multistep smart contracts, payment channels, and time-dependent conditions.

⏰ Absolute Timelocks

Specify an absolute point in time (block height or Unix timestamp) before which spending is prohibited.

  • nLockTime: Transaction-level field
  • CHECKLOCKTIMEVERIFY (CLTV): Output-level opcode (BIP65)

⏱️ Relative Timelocks

Specify an elapsed time from output confirmation before spending is allowed.

  • nSequence: Input-level field (BIP68)
  • CHECKSEQUENCEVERIFY (CSV): Output-level opcode (BIP112)

nLockTime: Transaction-Level Absolute Timelock

The nLockTime field exists in every transaction and defines the earliest time a transaction can be relayed and included in a block. 

// nLockTime interpretation:
if (nLockTime == 0)
    // Immediate propagation (most common)
else if (nLockTime < 500,000,000)
    // Interpret as BLOCK HEIGHT
    // Transaction invalid before specified block
else
    // Interpret as UNIX TIMESTAMP (seconds since 1970-01-01)
    // Transaction invalid before specified time

// Examples:
nLockTime = 0           // No restriction (99% of transactions)
nLockTime = 600,000     // Invalid before block 600,000
nLockTime = 1,700,000,000 // Invalid before Nov 2023

⚠️ nLockTime Limitation

Critical: nLockTime prevents spending until a time, but doesn't prevent double-spending before that time. The original signer can create a conflicting transaction without nLockTime and spend the same inputs earlier.

Solution: Use CHECKLOCKTIMEVERIFY (CLTV) to lock outputs directly, making early spending cryptographically impossible.

CHECKLOCKTIMEVERIFY (CLTV): Output-Level Absolute Timelock

CLTV (introduced December 2015, BIP65) is a per-output timelock that restricts when a UTXO can be spent, solving nLockTime's double-spend vulnerability. 

// Example: Time-locked payment to Bob (3 months from now)
// Without CLTV (vulnerable to double-spend):
DUP HASH160 <Bob's PubKey Hash> EQUALVERIFY CHECKSIG

// With CLTV (cryptographically enforced):
<now + 7,776,000 seconds> CHECKLOCKTIMEVERIFY DROP 
DUP HASH160 <Bob's PubKey Hash> EQUALVERIFY CHECKSIG

// Spending requirements:
// 1. Transaction nLockTime >= CLTV parameter
// 2. CLTV and nLockTime must use same format (blocks OR seconds)
// 3. Input nSequence must be < 0xFFFFFFFF

🎯 CLTV Use Case: Vesting Schedule

Company grants employee stock options vesting over 4 years. Create 48 monthly UTXOs with CLTV incrementing by ~4,380 blocks (30 days). Each output unlocks exactly when vesting occurs.

🔒 CLTV Use Case: Trust Fund

Parent creates P2SH output with CLTV set to child's 18th birthday. Funds cryptographically locked until that exact block height, with no possibility of early access.

CHECKSEQUENCEVERIFY (CSV): Output-Level Relative Timelock

CSV (activated May 2016, BIP112) creates relative timelocks measured from UTXO confirmation time rather than absolute clock/block values. Essential for payment channels and Lightning Network.

🔄 Relative Timelock Semantics

Absolute (CLTV): "Cannot spend until block 700,000" (fixed calendar date)
Relative (CSV): "Cannot spend until 100 blocks after this output is confirmed" (dynamic, depends on confirmation time) 

// nSequence encoding (BIP68):
// Bit 31: Disable flag (1 = disabled)
// Bit 22: Type flag (0 = blocks, 1 = time)
// Bits 0-15: Timelock value

// Examples:
nSequence = 100        // 100 blocks relative timelock
nSequence = (1<<22) | 144  // 144 * 512 seconds = ~20.48 hours

// CSV script example (100-block relative lock):
100 CHECKSEQUENCEVERIFY DROP
DUP HASH160 <PubKey Hash> EQUALVERIFY CHECKSIG

⚡ CSV + Lightning Network

CSV enables unilateral channel closure. When Alice closes a payment channel, her commitment transaction includes CSV-locked outputs giving Bob time to detect and penalize fraud (if Alice broadcasts an old state). The relative lock ensures dispute period regardless of when closure occurs.

⚡ Module 5: Segregated Witness (SegWit)

Activated August 2017 (BIPs 141-144) — SegWit fundamentally restructured Bitcoin transactions to fix transaction malleability, enable Layer 2 protocols, increase block capacity, and introduce script versioning.

5.1 The Transaction Malleability Problem

Transaction malleability is the ability to change a transaction's ID (TXID) without invalidating the transaction itself. This occurs because TXID is calculated from the entire transaction including signatures, and signatures can be modified in ways that remain mathematically valid but change the byte-level representation.

⚠️ Malleability Attack Scenarios

Problem: Bob creates transaction TX1 spending Alice's output. Mallory modifies TX1's signature (keeping it valid) creating TX1' with different TXID. Both versions are valid but only one can be mined.

Impact: If TX1' gets mined instead of TX1, any child transaction referencing TX1's TXID becomes invalid (broken UTXO chain). This prevents reliable multi-party protocols and payment channels.

🔧 SegWit's Malleability Solution

Witness Data Segregation: Move all signature data (witness) out of the transaction body into a separate witness structure. Calculate TXID from only the non-witness data.

Result: Modifying signatures changes witness structure but not TXID. Child transactions can safely reference parent TXIDs before confirmation since TXIDs are now fixed.

5.2 SegWit Transaction Structure

Legacy Transaction (Pre-SegWit)

Version: 4 bytes
Input Count: 1+ bytes
Inputs:
  - Previous TX Hash: 32 bytes
  - Previous TX Index: 4 bytes
  - scriptSig Length: 1+ bytes
  - scriptSig (signatures): variable
  - Sequence: 4 bytes
Output Count: 1+ bytes
Outputs:
  - Value: 8 bytes
  - scriptPubKey Length: 1+ bytes
  - scriptPubKey: variable
Locktime: 4 bytes

TXID = SHA256(SHA256(entire_tx))

SegWit Transaction

Version: 4 bytes
Marker: 0x00 (SegWit flag)
Flag: 0x01
Input Count: 1+ bytes
Inputs:
  - Previous TX Hash: 32 bytes
  - Previous TX Index: 4 bytes
  - scriptSig Length: 1 byte (0 for native)
  - scriptSig: empty or P2SH script
  - Sequence: 4 bytes
Output Count: 1+ bytes
Outputs: (same as legacy)
Witness: (separate structure)
  - For each input: witness stack items
Locktime: 4 bytes

TXID = SHA256(SHA256(tx without witness))

Weight Units: SegWit's Block Capacity Innovation

SegWit replaced the 1 MB block size limit with a 4 million weight unit (WU) limit, where witness data counts as 1 WU per byte and non-witness data counts as 4 WU per byte. 

// Weight Calculation Formula:
Transaction Weight = (Base Size × 4) + Witness Size

// Block Limit:
Legacy: 1,000,000 bytes max
SegWit: 4,000,000 weight units max

// Effective Capacity Increase:
Pure legacy transactions: ~1.0 MB (4M WU ÷ 4)
Pure SegWit transactions: ~2.7 MB practical (signatures ~65% of transaction)
Mixed block: ~1.8-2.2 MB typical

// Example SegWit Transaction:
Base size: 200 bytes → 200 × 4 = 800 WU
Witness size: 130 bytes → 130 × 1 = 130 WU
Total weight: 930 WU
Virtual size (for fees): 930 ÷ 4 = 232.5 vbytes

💡 Why Weight Units?

Incentivization: By making witness data "cheaper" (1 WU vs 4 WU), SegWit economically incentivizes SegWit adoption. More SegWit transactions fit in a block, miners earn more fees.

UTXO Set Optimization: Non-witness data affects UTXO set (stored in RAM). Witness data doesn't. Weight units reflect actual resource costs—UTXO growth costs 4× more than witness storage.

🌳 Module 6: Taproot & Schnorr Signatures

Activated November 2021 (BIPs 340-342) — Taproot represents Bitcoin's most significant privacy and efficiency upgrade, combining Schnorr signatures, MAST, and key aggregation for uniform transactions.

6.1 Schnorr Signatures: Mathematical Elegance

Schnorr signatures (proposed by Claus Schnorr in 1989) are cryptographically superior to ECDSA with provable security, linearity enabling aggregation, and smaller signature size.

🔐 ECDSA (Legacy)

  • Signature: (r, s) = ~72 bytes DER-encoded
  • No signature aggregation
  • No provable security reduction
  • Malleable signatures (fixable but complex)
  • Each signer = separate signature

✨ Schnorr (Taproot)

  • Signature: 64 bytes fixed (no DER encoding)
  • Native key aggregation (MuSig protocol)
  • Provably secure (discrete log hardness)
  • Non-malleable by design
  • N signers = 1 aggregated signature

🔑 Key Aggregation: The Game Changer

MuSig Protocol: Multiple parties can combine their public keys into a single aggregated public key, then create a single signature valid for that aggregated key. 

// 3-of-3 Multisig:
Legacy ECDSA: 3 public keys (99 bytes) + 3 signatures (216 bytes) = 315 bytes
Schnorr MuSig: 1 aggregated key (33 bytes) + 1 signature (64 bytes) = 97 bytes

Privacy: On-chain, looks identical to single-sig transaction!

Schnorr Signature Mathematics (Simplified)

// Key Generation:
private_key = random 256-bit integer (x)
public_key = x × G  (where G is generator point on secp256k1)

// Signing (message m):
1. Generate nonce: r = random 256-bit integer
2. Compute R = r × G
3. Compute challenge: e = Hash(R || public_key || m)
4. Compute signature: s = r + e × x
5. Signature = (R, s)  [64 bytes total]

// Verification:
1. Recompute challenge: e = Hash(R || public_key || m)
2. Verify: s × G == R + e × public_key  (linear equation!)
3. Accept if equation holds

// Linearity Property (enables aggregation):
(s₁ + s₂) × G == (R₁ + R₂) + e × (P₁ + P₂)
This allows combining multiple signatures into one!

6.2 Taproot: Unified Transaction Structure

Taproot creates a unified output structure where spending can occur via key path (looks like single-sig) or script path (reveals only executed script branch via MAST).

📊 Taproot Output Structure

                    Taproot Output (P2TR)
                            ┌─────────────────────────┐
                            │   Taproot Public Key    │ ← appears on-chain
                            │   (33 bytes, bech32m)   │
                            └─────────┬───────────────┘
                                      │
                    ┌─────────────────┴─────────────────┐
                    │                                   │
              Key Path Spend                    Script Path Spend
           ┌──────────────────┐            ┌──────────────────────┐
           │ Internal Key (P) │            │  Merkle Root (MR)    │
           │ + Schnorr sig    │            │  MAST of scripts     │
           └──────────────────┘            └──────┬───────────────┘
           Looks like                             │
           single-sig!                   ┌────────┴─────────┐
                                         │                  │
                                   Script A         ┌──────┴──────┐
                                (e.g., multisig)    │             │
                                                Script B      Script C
                                               (timelock)   (emergency)
                            
Taproot Tweak: Output_Key = Internal_Key + Hash(Internal_Key || Merkle_Root) × G

🔑 Key Path Spending (Common Case)

When: All parties agree (e.g., all multisig participants cooperate)
How: Provide single Schnorr signature for tweaked internal key
Privacy: Looks identical to single-sig on-chain
Efficiency: Smallest possible transaction size

📜 Script Path Spending (Fallback)

When: Key path unavailable (dispute, emergency, complex conditions)
How: Reveal script + Merkle proof + satisfy script conditions
Privacy: Only reveals executed script, not alternatives
MAST Benefit: 100 possible scripts? Reveal only 1 used

🎯 Taproot Privacy Innovation

A corporation with complex 5-of-7 multisig + emergency recovery + time-delayed vault scripts can:

  • Normal case: 5 officers sign → Key path spend → looks like simple single-sig to observers
  • Emergency: Use emergency script → reveals only that script, not the 5-of-7 or vault
  • Result: On-chain transactions look uniform, maximizing privacy and fungibility

Tapscript: Enhanced Script Opcodes

// Tapscript Improvements over Legacy Script:
1. OP_CHECKSIGADD: Batch signature verification
   - Replaces OP_CHECKMULTISIG (no off-by-one bug!)
   - More efficient, supports Schnorr signatures

2. OP_SUCCESS opcodes: Reserved for soft fork upgrades
   - OP_SUCCESS126 through OP_SUCCESS189
   - Any OP_SUCCESS in script → transaction valid
   - Enables future opcodes without hard fork

3. Unlimited script size (resource limits apply)

// Example Tapscript (2-of-3 multisig with Schnorr):
<PubKey A> OP_CHECKSIG
<PubKey B> OP_CHECKSIGADD
<PubKey C> OP_CHECKSIGADD
2 OP_EQUAL  // Check that sum of valid signatures == 2

// Much cleaner than legacy OP_CHECKMULTISIG!

⚡ Module 7: Lightning Network

Layer 2 Payment Channels (BOLT Specifications) — Lightning Network enables near-instant, low-fee Bitcoin payments through off-chain bidirectional payment channels with multi-hop routing.

7.1 Payment Channel Architecture

A payment channel is a bidirectional off-chain relationship between two parties where they can exchange unlimited payments without blockchain transactions, settling final state on-chain only when closing.

⚡ Lightning Channel Lifecycle

  1. Opening: Create 2-of-2 multisig funding transaction on-chain
  2. Updating: Exchange unlimited off-chain commitment transactions
  3. Closing: Publish latest commitment to blockchain (cooperative or unilateral)

📊 Scalability Comparison

On-Chain (Layer 1)
• 7 transactions/second max
• $1-50 fee per transaction
• 10-60 minute confirmation
• Every tx stored forever
Lightning (Layer 2)
• Millions of tx/second
• Fraction of 1¢ fee
• <1 second settlement
• Only 2 on-chain tx (open/close)

💡 Example: Coffee Purchases

Without Lightning:
• 30 coffees/month = 30 on-chain tx
• ~30 × $5 fee = $150 in fees
• Blockchain bloat: 30 × 250 bytes

With Lightning:
• Open channel (1 on-chain tx)
• 30 instant coffee payments off-chain
• Close channel (1 on-chain tx)
• Total fees: 2 × $5 = $10
• Blockchain: 2 × 250 bytes

Commitment Transactions: Enforcing State Updates

Each payment updates a pair of commitment transactions—one for Alice, one for Bob—representing the current channel balance. Old states are revoked via penalty mechanism. 

// Channel Setup (Funding Transaction):
Alice and Bob create 2-of-2 multisig with 1 BTC
  - Alice deposits: 0.6 BTC
  - Bob deposits: 0.4 BTC
  - Total capacity: 1 BTC

// Initial State (Commitment #0):
Alice's commitment: If broadcast, Alice gets 0.6 BTC, Bob gets 0.4 BTC (with CSV delay)
Bob's commitment: If broadcast, Bob gets 0.4 BTC, Alice gets 0.6 BTC (with CSV delay)

// After Alice pays Bob 0.1 BTC (Commitment #1):
Alice's commitment: Alice 0.5 BTC, Bob 0.5 BTC
Bob's commitment: Bob 0.5 BTC, Alice 0.5 BTC
Old commitments (#0) are REVOKED via penalty keys

// Revocation Mechanism:
1. When creating new state, parties exchange revocation keys for old state
2. If anyone broadcasts old state, counterparty can CLAIM ALL funds (penalty)
3. CSV timelocks give victim time to detect and punish cheating

HTLCs: Multi-Hop Routing

Hashed Timelock Contracts (HTLCs) enable routing payments through intermediate nodes without trust. If Alice→Bob→Charlie, Bob forwards payment without risk of loss.

🔄 HTLC Payment Flow

Alice wants to pay 0.01 BTC to Charlie (no direct channel)
Route: Alice → Bob → Charlie

1. Charlie generates secret preimage R, gives Alice Hash(R)

2. Alice → Bob HTLC:
   "I'll pay you 0.01 BTC if you reveal preimage of Hash(R) within 24 hours
    Otherwise, refund me after 24 hours"

3. Bob → Charlie HTLC:
   "I'll pay you 0.01 BTC if you reveal preimage of Hash(R) within 12 hours
    Otherwise, refund me after 12 hours"

4. Charlie reveals R to claim from Bob (he knows R!)

5. Bob sees R, uses it to claim from Alice

6. Alice's payment complete. Bob earned routing fee.

Security:
- If Charlie doesn't reveal R, HTLCs expire and everyone gets refunded
- Decreasing timelocks ensure upstream nodes can claim before downstream expires
- Onion routing hides full path from intermediaries

⚠️ Lightning Network Challenges & Solutions

Challenge: Liquidity Management

Cannot send more than channel capacity in one direction. Channels need rebalancing.

Solution: Circular rebalancing, submarine swaps, dual-funded channels

Challenge: Online Requirement

Must be online to receive and forward payments, detect fraud.

Solution: Watchtowers monitor channels, trigger penalties for fraud

Challenge: Channel Closure Costs

Unilateral closure requires on-chain tx with delay (CSV).

Solution: Encourage cooperative closure, eltoo proposal for simpler state updates

Challenge: Path Finding

Finding route with sufficient liquidity is NP-hard.

Solution: Probabilistic routing, trampoline payments, JIT (just-in-time) routing

📖 Complete Glossary

Comprehensive definitions for all 157 blockchain transaction concepts.

Core Transaction Concepts

Transaction
Data structure encoding value transfer between participants, containing inputs consuming previous outputs and outputs creating new spendable UTXOs.
UTXO (Unspent Transaction Output)
Indivisible chunk of bitcoin tracked by full nodes as spendable output. The UTXO set represents all available bitcoin in the system.
Transaction Input
Reference to previous output being spent, containing transaction ID, output index, unlocking script, and sequence number.
Transaction Output
Contains value in satoshis and locking script (scriptPubKey) defining spending conditions.
Satoshi
Smallest bitcoin unit: 0.00000001 BTC (10⁻⁸). Named after Bitcoin's creator Satoshi Nakamoto.
Transaction Fee
Implicit fee calculated as difference between sum of inputs and sum of outputs, incentivizing miners.

Script & Cryptography

Bitcoin Script
Stack-based, Forth-like scripting language defining spending conditions. Turing incomplete by design for security.
Locking Script (scriptPubKey)
Script defining conditions required to spend an output. Also called witness script or cryptographic puzzle.
Unlocking Script (scriptSig)
Script satisfying locking script conditions, typically containing signature and public key.
P2PKH (Pay-to-Public-Key-Hash)
Most common transaction type: OP_DUP OP_HASH160 <PubKeyHash> OP_EQUALVERIFY OP_CHECKSIG
ECDSA (Elliptic Curve Digital Signature Algorithm)
Cryptographic signature scheme used in legacy Bitcoin transactions for proving private key ownership.

Advanced Patterns (Tier 2)

Multisignature (M-of-N)
Script requiring M signatures from N public keys using CHECKMULTISIG opcode. Example: 2-of-3 multisig.
P2SH (Pay-to-Script-Hash)
Transaction type allowing complex scripts while keeping burden on spender. Uses OP_HASH160 <ScriptHash> OP_EQUAL
nLockTime
Transaction-level timelock specifying earliest block height or Unix timestamp for validity.
CHECKLOCKTIMEVERIFY (CLTV)
Output-level absolute timelock opcode (BIP65) restricting spending until specified time.
CHECKSEQUENCEVERIFY (CSV)
Relative timelock opcode (BIP112) requiring specified time elapsed since output confirmation.

Protocol Enhancements (Tier 3)

Segregated Witness (SegWit)
Protocol upgrade (BIP141) separating witness data from transactions, fixing malleability and increasing capacity.
Witness Data
Signature and script data moved outside transaction structure in SegWit, enabling malleability fix.
Bech32
Native SegWit address format (BIP173) using bc1 prefix with improved error detection.
Schnorr Signature
Signature scheme (BIP340) enabling key aggregation, batch verification, and linearity properties.
Taproot
Protocol upgrade (BIP341) enabling privacy-preserving smart contracts through Schnorr signatures and MAST.
MAST (Merkelized Alternative Script Trees)
Taproot feature organizing alternative scripts in Merkle tree, revealing only executed paths for privacy.
Lightning Network
Layer 2 protocol enabling off-chain transactions through bidirectional payment channels with on-chain settlement.
HTLC (Hashed Timelock Contract)
Contract enabling multi-hop payments with hash locks and timelocks, ensuring atomic success/failure.
PSBT (Partially Signed Bitcoin Transaction)
Standardized format (BIP174) for coordinating signature collection in multisig/hardware wallet workflows.
