Transaction Fundamentals

🟢 Foundational | 3 Sections | ~4 Weeks | Source: Antonopoulos Ch.6

1.1 What is a Transaction?

Tier 1
Definition: A transaction is a data structure that encodes the transfer of value between participants in the Bitcoin system. Each transaction is a public entry in Bitcoin's blockchain, the global double-entry bookkeeping ledger.

Transactions are the most important part of the bitcoin system. Everything else in bitcoin is designed to ensure that transactions can be created, propagated on the network, validated, and finally added to the global ledger of transactions (the blockchain).

A transaction contains several key components:

  • Version: Specifies the transaction format version number
  • Inputs (vin): An array of transaction inputs that reference previous transaction outputs being spent
  • Outputs (vout): An array of transaction outputs that create new spendable amounts
  • Locktime: Defines the earliest time or block height when the transaction can be added to the blockchain

Transaction ID (TXID): Each transaction has a unique identifier calculated as the double SHA256 hash of the transaction data. This serves as a permanent, unchangeable reference to the transaction.

💡 Real-World Example

Think of a Bitcoin transaction like a check. Just as a check specifies who is paying (the account it's drawn from), how much is being paid, and who receives the payment, a Bitcoin transaction specifies:

  • Inputs: Which previous outputs (your "account balance") you're spending from
  • Outputs: Where the bitcoin is going and how much
  • Change: Any leftover amount returned to you (like getting change from a cashier)

Python Example: Calculating Transaction ID 
import hashlib
import json

def calculate_txid(tx_data):
    """
    Calculate Transaction ID from transaction data.
    TXID = SHA256(SHA256(serialized_transaction))
    
    Args:
        tx_data: Dictionary containing transaction structure
        
    Returns:
        Hexadecimal TXID string (reversed for display)
    """
    # Serialize transaction (simplified for demonstration)
    tx_serialized = json.dumps(tx_data, sort_keys=True).encode()
    
    # First SHA256 hash
    first_hash = hashlib.sha256(tx_serialized).digest()
    
    # Second SHA256 hash (double hash)
    second_hash = hashlib.sha256(first_hash).digest()
    
    # Reverse byte order for display (Bitcoin convention)
    txid = second_hash[::-1].hex()
    
    return txid

    "version": 1,
    "inputs": [{

        "vout": 0,
        "scriptSig": "304502...0484ecc0...",
        "sequence": 4294967295
    }],
    "outputs": [
        {
            "value": 1500000,  # 0.015 BTC in satoshis

1.2 The UTXO Model

Tier 1
UTXO (Unspent Transaction Output): An indivisible chunk of bitcoin currency recorded on the blockchain and recognized as valid by the entire network. The UTXO set represents all currently spendable bitcoins.

Bitcoin uses an Unspent Transaction Output (UTXO) model rather than an account-based system like traditional banking. This fundamental difference affects how transactions are constructed and validated.

Key Characteristics:

  • Indivisible: UTXOs cannot be partially spent; they must be consumed entirely
  • Discrete: Each UTXO has a specific value in satoshis
  • Trackable: Full nodes track all UTXOs in the UTXO set (currently millions)
  • State-Based: Every transaction represents a state transition in the UTXO set

UTXO vs Account Model:

Aspect UTXO Model (Bitcoin) Account Model (Ethereum)
State Storage Set of unspent outputs Account balances
Transaction Consumes UTXOs, creates new UTXOs Debits one account, credits another
Partial Spending Not possible (must create change output) Directly supported
Privacy Better (multiple addresses/outputs) Lower (account history visible)

Wallet Balance: What we call a "wallet balance" is actually the sum of all UTXOs that the wallet can spend with its private keys. Wallets scan the blockchain to aggregate UTXO values.

💡 The Change-Making Analogy

Imagine buying a $1.50 coffee with physical currency:

  • Exact Change: One $1 bill + two quarters = $1.50 (like using exact UTXO)
  • Making Change: Give $5 bill → Receive $3.50 change (like consuming large UTXO, creating payment + change outputs)
  • Cannot Split: You can't tear a $5 bill in half (UTXOs are indivisible)

Similarly, if you have a 0.5 BTC UTXO and want to pay 0.015 BTC, you must:

  1. Consume the entire 0.5 BTC UTXO as input
  2. Create 0.015 BTC output to recipient
  3. Create ~0.484 BTC change output back to yourself
  4. Leave ~0.001 BTC as transaction fee

Bitcoin Script System

🟢 Foundational | 4 Sections | ~2 Weeks | Source: Antonopoulos Ch.6-7

2.1 Bitcoin Script Language

Tier 1
Bitcoin Script: A stack-based, Forth-like scripting language designed for expressing spending conditions. Intentionally Turing-incomplete to ensure deterministic execution and prevent infinite loops.

Bitcoin Script uses a Last-In-First-Out (LIFO) stack for all operations. Unlike Turing-complete languages like Ethereum's Solidity, Bitcoin Script cannot loop, ensuring every script completes in predictable time.

Key Characteristics:

  • Stack-Based Execution: All operations push/pop from a single stack
  • Left-to-Right Processing: Scripts execute sequentially from left to right
  • No Loops: Cannot create while/for loops, preventing infinite execution
  • ~100 Opcodes: Limited instruction set (many disabled for security)
  • Deterministic: Same input always produces same output across all nodes

Script Execution Model: Bitcoin validates transactions by combining the unlocking script (scriptSig) from the input with the locking script (scriptPubKey) from the referenced output, then executing the combined script.

💡 Why Turing-Incomplete?

Trade-off: Bitcoin prioritizes predictability over programmability.

  • Ethereum (Turing-complete): Can express complex logic but requires "gas" to prevent infinite loops, introducing economic complexity
  • Bitcoin (Turing-incomplete): Simpler, more predictable, every node knows execution cost before running script

This design choice reflects Bitcoin's focus on being a secure, predictable monetary system rather than a general-purpose computer.

2.3 Pay-to-Public-Key-Hash (P2PKH)

Tier 1
P2PKH: The most common Bitcoin transaction type. Requires the spender to provide a public key that hashes to a specified value, plus a valid signature from the corresponding private key.

Locking Script (scriptPubKey):

OP_DUP OP_HASH160 <PubKeyHash> OP_EQUALVERIFY OP_CHECKSIG

Unlocking Script (scriptSig):

<Signature> <PublicKey>

Execution Flow:

  1. Stack starts with unlocking script: [Signature, PublicKey]
  2. OP_DUP: Duplicates PublicKey → [Signature, PublicKey, PublicKey]
  3. OP_HASH160: Hashes top item → [Signature, PublicKey, Hash(PublicKey)]
  4. <PubKeyHash>: Pushes expected hash → [Signature, PublicKey, Hash(PublicKey), PubKeyHash]
  5. OP_EQUALVERIFY: Checks if hashes match, fails if not → [Signature, PublicKey]
  6. OP_CHECKSIG: Verifies signature against public key and transaction data
  7. Result: TRUE if signature valid, FALSE otherwise
💡 Why Hash the Public Key?

Security Benefits:

  • Shorter addresses: 160-bit hash vs 256-bit public key
  • Quantum resistance: Public key not revealed until spending
  • Address reuse protection: Each address can use new key pair

The hash provides an additional layer of security. Even if elliptic curve cryptography is broken, attacker still needs to reverse the hash function.

Python: P2PKH Script Validator 
import hashlib

def hash160(data):
    """HASH160: SHA256 followed by RIPEMD160"""
    sha256_hash = hashlib.sha256(data).digest()
    ripemd160 = hashlib.new('ripemd160')
    ripemd160.update(sha256_hash)
    return ripemd160.digest()

Cryptographic Foundations

🟢 Foundational | 3 Sections | ~2 Weeks | Source: Antonopoulos Ch.4,6

3.1 Cryptographic Hash Functions

Tier 1
Cryptographic Hash Function: A mathematical function that converts input data of arbitrary size into a fixed-size output (hash/digest) with specific security properties: collision resistance, preimage resistance, and avalanche effect.

Bitcoin's Hash Functions:

  • SHA256: 256-bit output, used for block hashing and transaction IDs
  • RIPEMD160: 160-bit output, used in address generation
  • HASH160: SHA256 followed by RIPEMD160, used for P2PKH addresses

Essential Properties:

  1. Deterministic: Same input always produces same output
  2. Quick Computation: Efficient to calculate hash from input
  3. Preimage Resistance: Computationally infeasible to reverse (one-way)
  4. Collision Resistance: Extremely unlikely to find two inputs with same hash
  5. Avalanche Effect: Small input change → completely different output

3.2 ECDSA Digital Signatures

Tier 1
ECDSA (Elliptic Curve Digital Signature Algorithm): Bitcoin's signature scheme using secp256k1 elliptic curve. Enables proving ownership of private key without revealing it.

Signature Components:

  • Private Key (d): 256-bit random number (keep secret!)
  • Public Key (Q): Point on elliptic curve: Q = d × G (where G is generator point)
  • Signature (r, s): Two 256-bit numbers proving knowledge of private key

Signature Creation Process:

  1. Hash the transaction data: z = HASH256(transaction)
  2. Generate random nonce: k
  3. Calculate point: (x, y) = k × G
  4. Compute r = x mod n
  5. Compute s = k⁻¹(z + rd) mod n
  6. Signature is (r, s)

Verification:

Verify s⁻¹(z×G + r×Q) has x-coordinate equal to r

If match: signature valid ✓ | If no match: signature invalid ✗

Advanced Transaction Patterns

🟡 Intermediate | 3 Sections | ~2 Weeks | Source: Antonopoulos Ch.7

4.1 Multisignature (M-of-N) Transactions

Tier 2
Multisignature: A script requiring M signatures from N possible public keys to spend funds. Common patterns: 2-of-3 (escrow), 3-of-5 (corporate accounts).

Multisig Script Pattern:

M <PubKey1> <PubKey2> ... <PubKeyN> N OP_CHECKMULTISIG

Example: 2-of-3 Multisig

2 <Alice_PubKey> <Bob_PubKey> <Charlie_PubKey> 3 OP_CHECKMULTISIG

To spend: Provide any 2 signatures from Alice, Bob, or Charlie

Use Cases:

  • Escrow Services: 2-of-3 with buyer, seller, arbitrator
  • Corporate Accounts: Require multiple executives to approve
  • Joint Accounts: Shared control between parties
  • Inheritance: Family members need to agree

CHECKMULTISIG Bug:

Due to an implementation bug that became consensus, OP_CHECKMULTISIG pops one extra item from stack. Unlocking script must include extra value (typically 0):

0 <Sig1> <Sig2> 2 <PK1> <PK2> <PK3> 3 OP_CHECKMULTISIG
💡 Real-World: Bitcoin Escrow

Scenario: Alice buys goods from Bob using Charlie as arbitrator

  • Happy path: Alice + Bob sign (2-of-3) → funds released
  • Dispute: Alice + Charlie OR Bob + Charlie sign → arbitrator decides
  • Security: No single party can steal funds

4.2 Pay-to-Script-Hash (P2SH)

Tier 2
P2SH (BIP16): Allows sender to pay to a hash of a script (redeem script) instead of the full script. The complex script is revealed only when spending, shifting size burden from sender to recipient.

P2SH Locking Script:

OP_HASH160 <20-byte-hash-of-redeem-script> OP_EQUAL

P2SH Unlocking Script:

<signatures> <redeem-script>

Advantages:

  1. Sender Simplicity: Sender only needs hash, not complex script
  2. Burden Shift: Recipient pays for complex script size
  3. Shorter Addresses: P2SH addresses start with "3"
  4. Privacy: Script type hidden until spending
  5. Flexibility: Can wrap any script pattern

Two-Stage Verification:

  1. First: Verify hash of redeem script matches
  2. Second: Execute redeem script with provided signatures
💡 P2SH Multisig: Before and After

Without P2SH (P2MS):

Locking: 2 <PK1> <PK2> <PK3> 3 OP_CHECKMULTISIG (292 bytes)
Address: Complex, non-standard, customer needs special software

With P2SH:

Locking: OP_HASH160 <20-byte-hash> OP_EQUAL (23 bytes)
Address: 3J98t1WpEZ73CNmYviecrnyiWrnqRhWNLy (standard, simple)

Benefits: 92% size reduction for sender, standard address format, recipient reveals complexity only when spending

4.3 Timelock Mechanisms

Tier 2
Timelocks: Restrictions that prevent spending until a future time or block height. Enable time-based smart contracts like payment channels, atomic swaps, and inheritance schemes.

Four Timelock Types:

Type Scope Time Reference
nLockTime Transaction-level Absolute (block/timestamp)
CLTV Output-level (BIP65) Absolute (block/timestamp)
nSequence Input-level Relative (blocks/time)
CSV Output-level (BIP112) Relative (blocks/time)

CHECKLOCKTIMEVERIFY (CLTV) Example:

<block_height> OP_CHECKLOCKTIMEVERIFY OP_DROP
OP_DUP OP_HASH160 <pubkey_hash> OP_EQUALVERIFY OP_CHECKSIG

Effect: Output cannot be spent until specified block height reached

Use Cases:

  • Payment Channels: Enable Lightning Network
  • Atomic Swaps: Cross-chain trading
  • Inheritance: Funds unlockable after death
  • Escrow: Refunds after timeout
  • Recurring Payments: Subscriptions

Segregated Witness (SegWit)

🔴 Advanced | 4 Sections | ~2 Weeks | Source: BIP141-144, BIP173

5.1 Transaction Malleability & The Motivation for SegWit

Tier 3
Transaction Malleability: The ability to change a transaction's ID without invalidating signatures. This creates problems for payment channels and layer-2 protocols that rely on unconfirmed transaction IDs.

The Problem:

TXID = HASH256(entire_transaction) includes signature data. Since signature encoding has flexibility (DER format allows multiple valid encodings), third parties could modify signatures without invalidating them, changing TXID.

Why This Matters:

  • Payment Channels Break: Lightning relies on chains of unconfirmed transactions
  • Wallet Confusion: User sees different TXID than expected
  • DoS Attacks: Flood network with malleated transactions
  • Smart Contracts Fail: Cannot reference future transaction IDs reliably

SegWit's Solution:

Remove signature data from TXID calculation. TXID now only covers transaction structure (inputs/outputs), not signatures.

Result: TXID becomes immutable, enabling Lightning Network and other layer-2 protocols.

5.2 SegWit Transaction Structure

Tier 3

Legacy vs SegWit Transaction Structure:

Field Legacy SegWit
Version 4 bytes 4 bytes
Marker - 0x00 (1 byte)
Flag - 0x01 (1 byte)
Input Count VarInt VarInt
Inputs With scriptSig scriptSig empty or minimal
Output Count VarInt VarInt
Outputs Standard Standard
Witness - Signature + PubKey data
Locktime 4 bytes 4 bytes

Key Innovation: Witness Field

Signature data moved to separate "witness" field that:

  • Is not included in TXID calculation (fixes malleability)
  • Gets 75% discount in block weight calculation (capacity increase)
  • Is optional for backward compatibility

Two Transaction IDs:

  • TXID: Hash of transaction without witness data (malleability-fixed)
  • WTXID: Hash of complete transaction including witness (for validation)

5.3 Native SegWit Outputs: P2WPKH & P2WSH

Tier 3

P2WPKH (Pay-to-Witness-Public-Key-Hash):

SegWit equivalent of P2PKH

Locking Script (scriptPubKey): OP_0 <20-byte-pubkey-hash>
Witness: <signature> <pubkey>

P2WSH (Pay-to-Witness-Script-Hash):

SegWit equivalent of P2SH

Locking Script (scriptPubKey): OP_0 <32-byte-script-hash>
Witness: <signatures> <witness-script>

Backward Compatibility: P2SH-Wrapped SegWit

For wallets not supporting native SegWit, wrap in P2SH:

P2SH-P2WPKH: OP_HASH160 <hash-of-segwit-script> OP_EQUAL

Address starts with "3" (P2SH) but spends as SegWit internally

Benefits Comparison:

Feature Native SegWit P2SH-SegWit
Fee Savings ~40% ~25%
Address Type bc1... (Bech32) 3... (Base58)
Compatibility Requires SegWit support Works with old wallets

5.4 Block Weight Units & Capacity Increase

Tier 3

Weight Unit Calculation:

Weight = (Base Size × 3) + Total Size
Where:
  Base Size = Transaction size without witness data
  Total Size = Complete transaction including witness

Max Block Weight = 4,000,000 weight units

Effect on Capacity:

  • Legacy block: 1 MB = 1,000,000 bytes = 4,000,000 WU
  • SegWit block: Can exceed 1 MB physical size while staying under 4M WU
  • Practical limit: ~2.7 MB with all SegWit transactions
  • Throughput increase: ~2x transactions per block

Fee Discount for Witness Data:

Witness bytes count as 0.25 WU instead of 1 WU, incentivizing SegWit adoption

## MODULE 6: TAPROOT & SCHNORR SIGNATURES (TIER 3 - ADVANCED)
6

Taproot & Schnorr Signatures

🔴 Advanced | 4 Sections | ~2 Weeks | Source: BIP340-342

6.1 Schnorr Signature Advantages

Tier 3
Schnorr Signatures: Alternative to ECDSA with mathematical properties enabling signature aggregation, batch verification, and provable security. Activated in Bitcoin November 2021 (BIP340).

Key Advantages Over ECDSA:

Feature ECDSA Schnorr
Signature Size 71-72 bytes (DER) 64 bytes (fixed)
Aggregation Not possible Linear aggregation
Batch Verification O(n) time O(1) time for n sigs
Provable Security Heuristic Proven secure
Linearity No Yes (key+sig aggregation)

Signature Aggregation Example:

3 signers in multisig:

  • ECDSA: 3 signatures × 72 bytes = 216 bytes
  • Schnorr: 1 aggregated signature = 64 bytes
  • Savings: 70% size reduction!

Batch Verification:

Verify 100 Schnorr signatures with same computational cost as verifying 1 signature. Dramatically improves node sync speed.

6.2 Taproot Output Construction

Tier 3

Core Concept:

Taproot allows outputs to be spent via two paths:

  1. Key Path: Single signature (appears as normal spend)
  2. Script Path: Execute one of multiple scripts from Merkle tree

Taproot Address Creation:

1. Start with internal key: P
2. Create script tree (MAST)
3. Compute Merkle root: M
4. Tweak key: Q = P + hash(P||M)×G
5. Taproot output: OP_1 <Q>

Spending Paths:

Key Path Spend (Common Case):

  • Provide single Schnorr signature for Q
  • No script revealed
  • Looks identical to normal single-sig
  • Privacy: Multisig/complex scripts indistinguishable from single-sig

Script Path Spend (Alternative Conditions):

  • Reveal one script from tree
  • Provide Merkle proof
  • Execute revealed script
  • Other scripts remain hidden

6.3 MAST: Privacy-Preserving Script Trees

Tier 3

Problem MAST Solves:

Without MAST, complex scripts with multiple conditions reveal all branches on-chain, even unexecuted ones. This wastes space and reduces privacy.

MAST Solution:

  1. Organize scripts in Merkle tree (TapTree)
  2. Commit to tree root in output
  3. When spending, reveal only executed branch
  4. Provide Merkle proof for validity

Example: Inheritance Wallet

Script Tree:
         Root
        /    \
    Owner   Emergency
    (key)   /      \
         Heir1   Heir2+Time

Spending scenarios:
- Owner spends: Key path (simple sig, tree hidden)
- Emergency w/ Heir1: Reveal only Heir1 script
- Emergency w/ Heir2: Reveal only Heir2+timelock script

Result: Unexecuted conditions never revealed on-chain

Benefits:

  • Privacy: Only executed path revealed
  • Efficiency: Don't pay for unexecuted scripts
  • Scalability: Log(n) proof size for n scripts
  • Flexibility: Unlimited script options

6.4 Tapscript: Enhanced Script Language

Tier 3

New Opcodes (BIP342):

Opcode Purpose
OP_CHECKSIGADD Efficient Schnorr multisig (replaces OP_CHECKMULTISIG)
OP_SUCCESS Reserved for future soft fork upgrades

OP_CHECKSIGADD Benefits:

Old (OP_CHECKMULTISIG): 2 <PK1> <PK2> <PK3> 3 OP_CHECKMULTISIG
New (OP_CHECKSIGADD): <PK1> OP_CHECKSIG <PK2> OP_CHECKSIGADD <PK3> OP_CHECKSIGADD 2 OP_NUMEQUAL
  • No CHECKMULTISIG dummy element bug
  • Works with key aggregation
  • More flexible thresholds
## MODULE 7: LIGHTNING NETWORK (TIER 3 - ADVANCED)
7

Lightning Network

🔴 Advanced | 4 Sections | ~2 Weeks | Source: BOLT Specs, Poon & Dryja 2016

7.1 Bidirectional Payment Channels

Tier 3
Payment Channel: Off-chain payment mechanism allowing unlimited transactions between two parties with only two on-chain transactions (open and close). Foundation of Lightning Network.

Channel Lifecycle:

1. Opening (On-Chain):

Alice and Bob create 2-of-2 multisig funding transaction
Alice: 0.5 BTC ┐
Bob:   0.5 BTC ├─→ [Funding TX] → 2-of-2 multisig (1 BTC)

2. Operating (Off-Chain):

  • Create commitment transactions allocating balance
  • Each payment = new commitment transaction
  • Old commitments invalidated via revocation
  • Speed: Instant (no blockchain confirmation needed)
  • Privacy: Only channel parties know transaction details
  • Cost: No fees except routing

3. Closing (On-Chain):

  • Cooperative: Both sign final state, broadcast to chain
  • Unilateral: One party broadcasts latest commitment
  • Breach Remedy: If old state broadcast, counterparty takes all funds (penalty)

Commitment Transaction Structure:

Commitment TX (Alice's version):
Inputs: Funding TX output
Outputs:
  1. To Alice: Immediate (her balance)
  2. To Bob: Timelock + revocation (his balance)

Revocation Mechanism:

When updating channel state:

  1. Create new commitment with updated balances
  2. Exchange revocation secrets for old commitment
  3. If old commitment broadcast → counterparty uses revocation secret to claim all funds

Security: Prevents cheating through economic incentive

7.2 Hashed Timelock Contracts (HTLCs)

Tier 3
HTLC: Smart contract combining hash lock and timelock, enabling atomic multi-hop payments. Recipient must reveal preimage (proof of payment) within timeout period or funds return to sender.

HTLC Structure:

IF
    <receiver_pubkey> OP_CHECKSIG
    <preimage_hash> OP_HASH160 OP_EQUAL
ELSE
    <timeout> OP_CHECKLOCKTIMEVERIFY OP_DROP
    <sender_pubkey> OP_CHECKSIG
ENDIF

Two ways to claim:

  1. Success Path: Receiver provides preimage + signature
  2. Timeout Path: After timeout, sender can reclaim funds

HTLC in Multi-Hop Payment:

Alice → Bob → Carol → Dave
Payment: 0.01 BTC

Step 1: Dave generates random preimage R, sends H(R) to Alice
Step 2: Alice → Bob: "Pay 0.01 BTC if you show preimage for H(R) within 100 blocks"
Step 3: Bob → Carol: "Pay 0.01 BTC if you show preimage for H(R) within 90 blocks"
Step 4: Carol → Dave: "Pay 0.01 BTC if you show preimage for H(R) within 80 blocks"
Step 5: Dave reveals R to Carol (claims payment)
Step 6: Carol reveals R to Bob (claims payment)
Step 7: Bob reveals R to Alice (claims payment)

Result: Payment succeeds atomically (all or nothing)

Security Properties:

  • Atomicity: Either all HTLCs succeed or all fail
  • No Trust Required: Cryptography enforces payment
  • Privacy: Only payment endpoints know amount/purpose
  • Timeout Protection: Funds not stuck forever

7.3 Lightning Network Routing

Tier 3

Network Structure:

  • Nodes: Lightning wallets maintaining payment channels
  • Channels: Bidirectional payment paths with capacity
  • Graph: Publicly announced channels form routing graph
  • Decentralized: No central coordinator

Routing Mechanisms:

1. Source Routing:

  • Sender calculates entire route
  • Knows all hops from source to destination
  • Similar to Tor onion routing

2. Onion Routing:

  • Each hop only knows previous and next node
  • Payment details encrypted in layers
  • Intermediaries don't know source/destination
  • Privacy: Payment metadata protected

Route Finding Algorithm:

1. Query channel graph for nodes with capacity
2. Calculate shortest path (considering fees & capacity)
3. Check liquidity along path
4. Construct onion-encrypted payment instructions
5. Send HTLC chain along route
6. Wait for preimage reveal or timeout

Routing Fees:

  • Base Fee: Fixed per transaction (e.g., 1 sat)
  • Proportional Fee: Percentage of amount (e.g., 0.01%)
  • Market-Driven: Node operators set competitive rates
  • Typical Cost: 0.1-1% for multi-hop payments

7.4 Channel Management & Security

Tier 3

Watchtowers:

Problem: Must monitor blockchain for cheating (old state broadcast)

Solution: Watchtowers monitor on your behalf

  • Give watchtower encrypted breach remedy transactions
  • If breach detected, watchtower broadcasts penalty
  • Enables mobile wallets (don't need 24/7 monitoring)

Channel Rebalancing:

Problem: Channels become one-sided (can't route)

Solutions:

  • Circular Rebalancing: Pay yourself through network
  • Submarine Swaps: Exchange on-chain ↔ off-chain
  • Liquidity Marketplaces: Buy/sell inbound capacity

Security Considerations:

Threat Mitigation
Channel Breach Penalty transactions + watchtowers
Routing Failure HTLCs timeout, funds returned
Data Loss Channel backups, static backups
Privacy Leaks Onion routing, channel type mixing
