📋 Module 1: Transaction Fundamentals

Understanding the core structure and mechanics of blockchain transactions.

1.1 What is a Bitcoin Transaction?

Transactions are the most important part of the bitcoin system. Everything in Bitcoin is designed to ensure that transactions can be created, propagated on the network, validated, and finally added to the global ledger of transactions (the blockchain).

💡 Key Insight: Transactions are data structures that encode the transfer of value between participants in the Bitcoin system. Each transaction is a public entry in Bitcoin's blockchain, the global double-entry bookkeeping ledger.

A Bitcoin transaction is fundamentally different from traditional payment systems. Rather than moving funds from one account to another, Bitcoin transactions consume previously created outputs and create new outputs that can be consumed in future transactions. This creates an unbroken chain of value transfer from the creation of bitcoin through mining to the present day.

1.2 Transaction Structure: Behind the Scenes

What you see in a blockchain explorer is very different from what a transaction actually contains. Most high-level constructs like "addresses" and "balances" don't actually exist in the transaction data—they're abstractions created for user convenience.

Example: Raw Transaction Structure

{
  "version": 1,
  "locktime": 0,
  "vin": [{
    "txid": "7957a35f...999f6f18",
    "vout": 0,
    "scriptSig": "3045022100...[signature]...",
    "sequence": 4294967295
  }],
  "vout": [{
    "value": 0.01500000,
    "scriptPubKey": "OP_DUP OP_HASH160 ab68025... OP_EQUALVERIFY OP_CHECKSIG"
  }, {
    "value": 0.08450000,
    "scriptPubKey": "OP_DUP OP_HASH160 7f9b1a7... OP_EQUALVERIFY OP_CHECKSIG"
  }]
}
⚠️ Important: In Bitcoin, there are no coins, no senders, no recipients, no balances, no accounts, and no addresses at the protocol level. All of these concepts are constructed at a higher level for user convenience.

Core Transaction Components

Component Description Purpose
version Transaction version number Specifies which rules to use for validation
locktime Unix timestamp or block number Earliest time transaction can be added to blockchain
vin Array of transaction inputs References to outputs being spent
vout Array of transaction outputs New outputs created by this transaction

1.3 The UTXO Model: Understanding Bitcoin's Accounting System

The fundamental building block of a Bitcoin transaction is a transaction output. Transaction outputs are indivisible chunks of bitcoin currency, recorded on the blockchain and recognized as valid by the entire network.

🔑 Key Concept: UTXO (Unspent Transaction Output)

UTXO stands for Unspent Transaction Output. Bitcoin full nodes track all available and spendable outputs in what's called the UTXO set. The UTXO set currently numbers in the millions of individual outputs.

Every transaction represents a state transition in the UTXO set: consuming (spending) existing UTXOs and creating new ones.

💰 Understanding "Balance" in Bitcoin

When we say a user's wallet has "received" bitcoin, what we really mean is that the wallet has detected a UTXO that can be spent with one of the keys controlled by that wallet.

A user's bitcoin "balance" is the sum of all UTXO that the user's wallet can spend, which may be scattered among hundreds of transactions and hundreds of blocks. The concept of balance is created by the wallet application, not by the Bitcoin protocol.

📊 UTXO Set Dynamics

✅ Wallet UTXO Set
UTXO #1: 0.5 BTC
UTXO #2: 0.3 BTC
UTXO #3: 0.2 BTC
Total: 1.0 BTC
🔄 After Transaction
UTXO #1: 0.5 BTC (spent)
UTXO #2: 0.3 BTC
UTXO #3: 0.2 BTC
UTXO #4: 0.3 BTC (change)
Total: 0.8 BTC
(0.2 BTC sent + 0.001 BTC fee)

Critical UTXO Properties

🔒 Indivisible

UTXOs cannot be divided. If a UTXO is larger than the desired payment amount, it must be consumed in its entirety and change must be generated.

Example: To pay 1 BTC from a 20 BTC UTXO, you must consume all 20 BTC and create two outputs: 1 BTC to recipient, 19 BTC back as change.
📏 Discrete Units

Outputs are discrete units of value denominated in integer satoshis. One bitcoin can be divided down to eight decimal places (100,000,000 satoshis = 1 BTC).

Satoshi: The smallest unit in Bitcoin, named after its creator. 1 satoshi = 0.00000001 BTC

🔐 Module 2: Transaction Inputs and Outputs Deep Dive

Understanding how transactions consume and create value through inputs and outputs.

2.1 Transaction Outputs: Creating Spendable Value

Every Bitcoin transaction creates outputs, which are recorded on the blockchain ledger. Almost all of these outputs create spendable chunks of bitcoin called UTXO, which are recognized by the whole network and available for the owner to spend in a future transaction.

📦 Transaction Output Components

Transaction outputs consist of two critical parts:

  1. An amount of bitcoin, denominated in satoshis (the smallest bitcoin unit)
  2. A cryptographic puzzle (locking script) that determines the conditions required to spend the output

Output Structure in JSON

"vout": [
  {
    "value": 0.01500000,
    "scriptPubKey": "OP_DUP OP_HASH160 ab68025513c3dbd2f7b92a94e0581f5d50f654e7 
                     OP_EQUALVERIFY OP_CHECKSIG"
  },
  {
    "value": 0.08450000,
    "scriptPubKey": "OP_DUP OP_HASH160 7f9b1a7fb68d60c536c2fd8aeaa53a8f3cc025a8 
                     OP_EQUALVERIFY OP_CHECKSIG"
  }
]
💡 Key Insight: The scriptPubKey (locking script) is also known as a:
  • Locking script (what we call it in this course)
  • Witness script (in SegWit context)
  • Cryptographic puzzle (conceptual term)

Output Serialization Format

Size Field Description
8 bytes Amount Bitcoin value in satoshis (10⁻⁸ bitcoin), little-endian format
1-9 bytes Locking-Script Size VarInt encoding of script length in bytes
Variable Locking-Script Script defining spending conditions
⚙️ Technical Note: Values are stored as 64-bit integers in little-endian byte order, meaning the least significant byte comes first. For example, 1,500,000 satoshis (0.015 BTC) becomes 60 e3 16 in little-endian hexadecimal.

2.2 Transaction Inputs: Consuming Previous Outputs

Transaction inputs identify which UTXO will be consumed and provide proof of ownership through an unlocking script. To build a transaction, a wallet selects from the UTXO it controls—choosing UTXO with enough value to make the requested payment.

🔑 Transaction Input Components

Each input contains four essential elements:

  1. Transaction ID (txid): References the transaction containing the UTXO being spent
  2. Output Index (vout): Identifies which specific output from that transaction (zero-indexed)
  3. Unlocking Script (scriptSig): Satisfies the conditions placed on the UTXO, unlocking it for spending
  4. Sequence Number: Used for transaction replacement and timelocks

Input Structure in JSON

"vin": [{
  "txid": "7957a35fe64f80d234d76d83a2a8f1a0d8149a41d81de548f0a65a8a999f6f18",
  "vout": 0,
  "scriptSig": "3045022100884d142d....[signature]....
                0484ecc0d46f1918b309....[public key]....",
  "sequence": 4294967295
}]

📊 Input-Output Relationship

Previous Transaction (txid: 7957...6f18)
Output[0]: 0.1 BTC → Your Address
Output[1]: 0.05 BTC → Another Address
↓ Referenced by Input
Current Transaction
Input:
- txid: 7957...6f18
- vout: 0 (referencing Output[0])
- scriptSig: [signature + public key]
Output[0]: 0.015 BTC → Bob's Cafe
Output[1]: 0.0845 BTC → Change to Your Address
Implied Fee: 0.1 - (0.015 + 0.0845) = 0.0005 BTC
⚠️ Critical Understanding: Transaction inputs do NOT explicitly state the value being spent! To know the input value, you must retrieve the referenced UTXO from the blockchain. This is why validators must look up previous transactions to verify the current one.

2.3 Transaction Fees: The Economic Incentive

Transaction fees are a crucial part of Bitcoin's economic model, providing incentives for miners to include transactions in blocks. Understanding how fees work is essential for creating valid transactions.

💰 Fee Calculation Formula

Fees = Sum(Inputs) − Sum(Outputs)

The fee is implicit—there's no fee field in the transaction structure. Any excess amount remaining after all outputs are deducted from all inputs becomes the miner's fee.

📊 Fee Calculation Example

Inputs
UTXO #1: 0.8 BTC
UTXO #2: 0.3 BTC
Total Inputs: 1.1 BTC
Outputs
Payment: 0.5 BTC
Change: 0.599 BTC
Total Outputs: 1.099 BTC
Fee: 0.001 BTC
🚨 Common Mistake: If you forget to create a change output, the entire "leftover" amount becomes the transaction fee! For example, consuming a 20 BTC UTXO to pay 1 BTC without creating a 19 BTC change output means you just paid a 19 BTC fee to the miner.

⚙️ Dynamic Fee Estimation

Modern Bitcoin wallets use dynamic fee estimation based on network congestion. Fees are typically measured in satoshis per byte (sat/byte or sat/vB for virtual bytes in SegWit).

🚀 High Priority

80+ sat/byte

Next block confirmation (0-1 blocks)

⏱️ Medium Priority

40-60 sat/byte

3-6 blocks (~30-60 minutes)

🐌 Low Priority

20-30 sat/byte

6+ blocks (1+ hours)

💡 Important: Static fees are no longer viable. Wallets that set static fees produce poor user experience as transactions may get "stuck" in the mempool, remaining unconfirmed for extended periods.

2.4 Change Outputs: Managing UTXO Indivisibility

Because UTXOs are indivisible, most Bitcoin transactions generate change. Understanding change outputs is crucial for both wallet developers and users who construct raw transactions.

🏪 Real-World Analogy

Imagine buying a $1.50 beverage. You reach into your wallet and find:

  • Exact change: $1 bill + 2 quarters = perfect!
  • Overpayment: $5 bill → receive $3.50 change
  • Multiple small bills: 6 quarters → exact amount

Bitcoin transactions work the same way. The wallet automatically selects UTXOs and creates change when necessary—users never see this complexity.

⚙️ Wallet Optimization: Wallets implement various UTXO selection algorithms:
  • First-fit: Use first available UTXO that meets the requirement
  • Best-fit: Select UTXO closest to required amount (minimize change)
  • Coin selection: Balance between transaction size and privacy

🔐 Module 3: Bitcoin Script Language and Validation

Understanding the programmable scripting system that secures Bitcoin transactions.

3.1 What is Bitcoin Script?

The Bitcoin transaction script language, called Script, is a Forth-like reverse-polish notation stack-based execution language. Both the locking script (placed on a UTXO) and the unlocking script (provided when spending) are written in this language.

🎯 Script Design Philosophy

Script is deliberately designed to be:

  • Simple: Limited scope, minimal processing requirements
  • Predictable: Deterministic execution, no randomness
  • Stateless: No state before or after execution
  • Turing Incomplete: No loops or complex flow control
  • Secure: Cannot create denial-of-service vulnerabilities
💡 Key Insight: Bitcoin transaction validation is not based on static patterns but achieved through execution of a scripting language. This allows for a nearly infinite variety of conditions to be expressed—the power of "programmable money."

⚙️ Turing Incompleteness: A Security Feature

Script contains many operators but deliberately lacks loops and complex flow control. This ensures the language is not Turing Complete, meaning scripts have limited complexity and predictable execution times.

✅ Benefits of Turing Incompleteness
  • Prevents infinite loops
  • Blocks "logic bombs"
  • Ensures predictable execution time
  • Protects against DoS attacks
  • Every transaction validated by every full node
❌ What Script Cannot Do
  • Create loops (for, while)
  • Maintain state between executions
  • Access external data
  • Perform arbitrary computations
  • Execute unpredictably

3.2 Stack-Based Language: Understanding the Stack

Script uses a data structure called a stack—a Last-In-First-Out (LIFO) queue. Think of it like a stack of cards where you can only add or remove from the top.

📚 Stack Operations

PUSH

Adds an item on top of the stack

Stack: [3, 2, 1]
↓ PUSH 4
Stack: [4, 3, 2, 1]
POP

Removes the top item from the stack

Stack: [4, 3, 2, 1]
↓ POP → 4
Stack: [3, 2, 1]

📊 Script Execution Example: 2 3 OP_ADD 5 OP_EQUAL

Step 1:
PUSH 2
Stack: [2]
Step 2:
PUSH 3
Stack: [3, 2]
Step 3:
OP_ADD
Pop 3, Pop 2
3 + 2 = 5
Stack: [5]
Step 4:
PUSH 5
Stack: [5, 5]
Step 5:
OP_EQUAL
Pop 5, Pop 5
5 == 5 → TRUE
Stack: [TRUE]
Result:
✅
Valid!
TRUE on stack
💡 Key Point: A script is valid if and only if the top item on the stack is TRUE (represented by the number 1 or any non-zero value) after execution. FALSE is represented by zero or an empty stack.

3.3 Locking and Unlocking Scripts

Bitcoin's validation engine uses two types of scripts that work together to validate transactions:

🔒 Locking Script (scriptPubKey)

A spending condition placed on an output. It specifies the conditions that must be met to spend the output in the future.

Also known as:

  • scriptPubKey (legacy name)
  • Witness script (SegWit context)
  • Cryptographic puzzle

🔓 Unlocking Script (scriptSig)

A script that "solves" or satisfies the conditions placed on an output by a locking script, allowing the output to be spent.

Also known as:

  • scriptSig (legacy name)
  • Witness (SegWit context)

⚙️ Script Validation Process

1️⃣ Copy Unlocking Script from Current Transaction Input
<Signature> <Public Key>
↓
2️⃣ Retrieve Locking Script from Referenced UTXO
OP_DUP OP_HASH160 <PubKeyHash> OP_EQUALVERIFY OP_CHECKSIG
↓
3️⃣ Concatenate and Execute Combined Script
<Signature> <Public Key> OP_DUP OP_HASH160 <PubKeyHash> OP_EQUALVERIFY OP_CHECKSIG
↓
4️⃣ Validation Result
✅

Input is valid if and only if execution results in TRUE on the stack

🔐 Security Note: The UTXO is permanently recorded in the blockchain and is unaffected by failed spending attempts. Only a valid transaction that correctly satisfies the conditions of the output results in the output being considered "spent" and removed from the UTXO set.

3.4 P2PKH: The Most Common Transaction Type

Pay-to-Public-Key-Hash (P2PKH) is the most common transaction script pattern, used in the majority of Bitcoin transactions. It's what people typically mean when they talk about "sending bitcoin to an address."

🔑 P2PKH Script Pattern

Locking Script (scriptPubKey):
OP_DUP OP_HASH160 <PubKeyHash> OP_EQUALVERIFY OP_CHECKSIG
Unlocking Script (scriptSig):
<Signature> <Public Key>

🔄 P2PKH Execution Step-by-Step

Combined Script:

<Sig> <PubKey> OP_DUP OP_HASH160 <PubKeyHash> OP_EQUALVERIFY OP_CHECKSIG
Step 1: PUSH <Sig>
[Sig]
Step 2: PUSH <PubKey>
[PubKey, Sig]
Step 3: OP_DUP
[PubKey, PubKey, Sig]
Step 4: OP_HASH160
[PubKeyHash', PubKey, Sig]
Step 5: PUSH <PubKeyHash>
[PubKeyHash, PubKeyHash', PubKey, Sig]
Step 6: OP_EQUALVERIFY
Verify hashes equal
[PubKey, Sig]
Step 7: OP_CHECKSIG
Verify signature
[TRUE]
✅ VALID
🔐 What P2PKH Proves:
  1. The public key hashes to the expected public key hash (proves address ownership)
  2. The signature is valid for this transaction and public key (proves private key ownership)

📖 Complete Glossary

Comprehensive definitions for all 157 blockchain transaction concepts.

Core Transaction Concepts

Transaction
Data structure encoding value transfer between participants, containing inputs consuming previous outputs and outputs creating new spendable UTXOs.
UTXO (Unspent Transaction Output)
Indivisible chunk of bitcoin tracked by full nodes as spendable output. The UTXO set represents all available bitcoin in the system.
Transaction Input
Reference to previous output being spent, containing transaction ID, output index, unlocking script, and sequence number.
Transaction Output
Contains value in satoshis and locking script (scriptPubKey) defining spending conditions.
Satoshi
Smallest bitcoin unit: 0.00000001 BTC (10⁻⁸). Named after Bitcoin's creator Satoshi Nakamoto.
Transaction Fee
Implicit fee calculated as difference between sum of inputs and sum of outputs, incentivizing miners.

Script & Cryptography

Bitcoin Script
Stack-based, Forth-like scripting language defining spending conditions. Turing incomplete by design for security.
Locking Script (scriptPubKey)
Script defining conditions required to spend an output. Also called witness script or cryptographic puzzle.
Unlocking Script (scriptSig)
Script satisfying locking script conditions, typically containing signature and public key.
P2PKH (Pay-to-Public-Key-Hash)
Most common transaction type: OP_DUP OP_HASH160 <PubKeyHash> OP_EQUALVERIFY OP_CHECKSIG
ECDSA (Elliptic Curve Digital Signature Algorithm)
Cryptographic signature scheme used in legacy Bitcoin transactions for proving private key ownership.

Advanced Patterns (Tier 2)

Multisignature (M-of-N)
Script requiring M signatures from N public keys using CHECKMULTISIG opcode. Example: 2-of-3 multisig.
P2SH (Pay-to-Script-Hash)
Transaction type allowing complex scripts while keeping burden on spender. Uses OP_HASH160 <ScriptHash> OP_EQUAL
nLockTime
Transaction-level timelock specifying earliest block height or Unix timestamp for validity.
CHECKLOCKTIMEVERIFY (CLTV)
Output-level absolute timelock opcode (BIP65) restricting spending until specified time.
CHECKSEQUENCEVERIFY (CSV)
Relative timelock opcode (BIP112) requiring specified time elapsed since output confirmation.

Protocol Enhancements (Tier 3)

Segregated Witness (SegWit)
Protocol upgrade (BIP141) separating witness data from transactions, fixing malleability and increasing capacity.
Witness Data
Signature and script data moved outside transaction structure in SegWit, enabling malleability fix.
Bech32
Native SegWit address format (BIP173) using bc1 prefix with improved error detection.
Schnorr Signature
Signature scheme (BIP340) enabling key aggregation, batch verification, and linearity properties.
Taproot
Protocol upgrade (BIP341) enabling privacy-preserving smart contracts through Schnorr signatures and MAST.
MAST (Merkelized Alternative Script Trees)
Taproot feature organizing alternative scripts in Merkle tree, revealing only executed paths for privacy.
Lightning Network
Layer 2 protocol enabling off-chain transactions through bidirectional payment channels with on-chain settlement.
HTLC (Hashed Timelock Contract)
Contract enabling multi-hop payments with hash locks and timelocks, ensuring atomic success/failure.
PSBT (Partially Signed Bitcoin Transaction)
Standardized format (BIP174) for coordinating signature collection in multisig/hardware wallet workflows.
